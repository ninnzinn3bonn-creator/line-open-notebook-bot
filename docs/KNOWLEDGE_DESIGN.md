# Knowledge構成・登録方法の調査と初期案

2026-09-11。要件正本: [REQUIREMENTS_v0.5.md](REQUIREMENTS_v0.5.md)。本書は公式情報から確認できる動作と、本PoC向けの設計判断を分けて記録する。実稼働版での検証は未実施。

## 合意済みの前提

Open Notebook全体をこのBotの回答用Knowledgeとして使用する。登録するのは承認済みの回答資料だけとし、全体検索で開始する。Notebook単位の検索制限はPoC必須要件にしない。

## 公式情報から確認したこと

| 確認事項 | 今回への意味 |
|---|---|
| Search/Askは範囲省略時にKnowledge全体を検索する [1] | 全体検索の方針と一致する |
| ベクトル検索はEmbedding済み本文を使い、タイトルだけは意味検索の対象にならない [1] | 対象施設・サービス・カテゴリ・条件は本文にも記載する |
| SourcesだけでなくNotes/Insightsも検索され得る [1][2] | AIの生成結果を自動的に正式Knowledgeへ戻さない |
| Source投入では本文抽出とEmbedding、指定されたTransformationが別工程になっている [3] | アップロード成功だけでは評価開始できない。処理と索引の完了を確認する |
| Source APIの取込にはtext/content、title、embed等が用意されている [4] | JSONを検証し、読みやすい本文へ整形してHTTP APIで投入する案が取れる |

公式の概念ガイドとAPI実装にはNotebook所属等の説明差があるため、所属数・タグ操作・更新可否をガイドだけで実装前提にしない。[5][4] 起動した固定版のOpenAPIと実応答を優先する。

## 本PoC向けの構成案

初期は1つのNotebook「問い合わせBot・回答資料」を使う。以下は管理上の見え方であり、フォルダ機能の存在を前提にした指定ではない。

```text
問い合わせBot・回答資料
  [予約] faq-001 団体予約
  [営業時間] faq-002 対応時間
  [キャンセル] faq-003 取消条件
  [設備] faq-004 駐車場
```

カテゴリと安定IDで担当者が探しやすくする。表示順・Notebook説明・タグだけで検索順位や回答制御が保証されるとは扱わない。カテゴリが増えた場合は管理上のNotebook分割を検討してよいが、検索は全体のままとする。

初期案の「1FAQ＝1Source」は、誤回答の原因追跡、条件の保持、個別差替えを容易にするための設計判断であり、Open Notebook公式が推奨する唯一の最適粒度ではない。極端に短い関連FAQが同一規程を共有する場合は、複数を小さな業務単位でまとめる案も比較する。

## 登録本文

原データは要件第11章のJSONを維持し、投入時は次の形式へ整形する。以下はテンプレートであり、実在の業務条件を示していない。

```text
FAQ ID: faq-001
カテゴリ: 予約
対象施設・サービス: ＜正式名称＞
件名: 団体予約

質問:
＜標準的な質問＞

正式回答:
＜承認済みの回答＞

適用条件:
＜人数・対象プラン・受付経路等＞

例外・対象外:
＜例外がある場合に記載＞

適用期間:
＜開始日・終了日が定められている場合に記載＞

出典:
＜承認済みの規程名・FAQ管理番号等＞

更新日:
＜更新日＞
```

条件・例外・適用期間は回答と同じSource内に置く。未記載を「条件なし」と補完しない。金額では単位・税込/税別・適用対象を、日時では曜日・休業日・適用期間を、原資料にある範囲で残す。「上記と同じ」「通常どおり」だけの記述は対象を明記できるか確認する。

構造化FAQはまずテキスト投入で検証し、不要なPDF/OCR変換を増やさない。元が長い業務資料の場合は見出し単位を検討し、適用条件や表の注記を切り落とさない。固定文字数の最適値は決め打ちせず、実際のチャンク境界を確認する。

安定ID、category、source、updatedAt等は原データの管理情報として保持する。追加する対象・期間等のフィールドは実Q&Aを見てSchemaへ定義し、Open Notebookが任意のメタデータを自動フィルタとして解釈すると仮定しない。

## 初期投入・更新手順

1. 原データのID重複・必須欄・矛盾する現行回答を確認する。
2. テキスト化して投入し、Source IDとFAQ ID、本文ハッシュ、Knowledge Revisionを対応付ける。
3. 抽出本文、処理状態、Embedding完了を確認する。Notes/Insightsの自動生成設定も確認する。
4. 代表質問で検索根拠と条件の取得を確認し、その後に全Golden Datasetを実行する。
5. 更新はPoCの応答処理を一時停止して行い、旧版のバックアップ、差替え、再索引、旧版除去確認、回帰評価後に再開する。失敗時は旧版を復元する。

全体検索では、別Notebookへ旧版を移すだけでは検索除外にならない。旧版の保存は検索外のバックアップ等で行い、Source削除・関連索引の除去が正しく反映されるか実機で確認する。退避中の新版を同じ検索対象へ追加して無停止切替できるとは仮定しない。

クライアントがUIで更新する運用を維持する。UIで変更した実内容は評価時にHTTP API等で取得し、対応表とRevisionへ反映する。以後のimportで古いJSONを自動上書きしない。Source本文を直接編集できない版では、UIで旧資料を置換する手順を案内する。

## 最小の検証計画

資料構成を比較する際は、モデル・Embedding・問い合わせ経路・評価質問を固定する。まず実Q&Aの代表5〜10問程度で登録粒度を確認し、問題がなければPoC必須の30〜50問以上へ進む。代表質問だけでPoCを合格にしない。

確認するケース:

- 標準質問と言い換えで必要なFAQが見つかる。
- 数字・キャンセル・例外条件が、本文の分割で欠落しない。
- 複数条件の質問で必要な資料を参照できる。
- 情報なしの場合に未登録の事実を補わない。
- 差替え後に旧料金・旧条件を回答しない。
- 同じIDを再投入しても検索結果の重複が増えない。

必要な場合のみ「1FAQ単位」と「関連する小規程単位」を比較する。検索で必要な根拠が得られた割合、条件欠落、重複、回答の人間評価、Latency、更新作業の手間を記録する。検索結果・出典がAPIで取得できない場合はUIでの根拠確認等を補助証拠とし、自動測定した指標と区別する。
